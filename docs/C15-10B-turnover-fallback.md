# C15-10B 0186 핵심 시각 수집 및 최신 자료 대체

개발 폴더에서만 구현·검증했다. 운영 Collector·스케줄·API 키·운영 DB는 수정하지 않았고 실전 API 호출·Telegram 발송·commit/push·운영 배포도 하지 않았다. 운영 코드/설정은 실행하지 않고 파일만 읽었으며 SQLite는 기존 `mode=ro`, `query_only=ON` 연결을 사용했다.

## A. 실제 수집 일정과 이번 수정

운영 `workflow-config.json`은 `profile=c12x-23-8`, `turnover_max_pages=1`, `telegram_send_enabled=false`다. 시작 스크립트와 `run_real_collector.py`가 기존 C12X 스케줄을 사용함을 소스로 확인했다. 준비 점검이나 실행 명령도 실제로 호출하지 않았다.

| 대상 | 현재 정책/사실 |
|---|---|
| 운영 0198 | 09:10~09:55 5분 간격, 10:00~16:00 30분 간격. 하루 23개 슬롯. 09:40/09:45/09:50 모두 포함. |
| 운영 0186 | 09:40, 09:50, 10:00, 11:00, 14:00, 14:30, 15:00, 15:30. **09:45 없음**, 총 8개. |
| 개발 0186 | 기존 C15 코드에 이미 09:45가 포함된 9개 슬롯. 세 핵심 시각에 0198/0186 모두 수집하도록 되어 있음. |
| 실제 11/05 09:45 ledger | `ranking_result=0`으로 0198 성공, `turnover` 항목 없음. 수집 실패 재시도 문제가 아니라 현재 운영 일정에 없는 상태. |

개발 `TURNOVER_SLOTS`와 `C12X_SLOTS`의 세 핵심 시각이 각각 **한 번씩만** 있는지 검사했다. 이미 충족해 스케줄 상수를 다시 수정하거나 시각을 중복 추가하지 않았다. 기존 `Workflow`에서 슬롯별 0186 파일이 있으면 재호출하지 않는 동작도 유지했다.

요청 간격은 기존 공유 요청 시계를 이어받아 `max(1.2, client.request_interval)`초다. 0186은 페이지마다 기존 호출을 사용하고 현재 한 페이지에서 멈춘다. 추가 페이지는 연속조회 조건과 최대 페이지 설정 1~10의 기존 경로를 따르며 이번에 페이지 수나 재시도/재인증 정책을 늘리지 않았다. 운영에 09:45를 추가하면 현재 한 페이지 기준 정규 0186 요청이 하루 8→9회로 1회 늘어난다. 이는 현재 코드의 페이싱 확인이며 제공사 전체 호출 한도를 새로 인증했다는 뜻은 아니다.

## B. 대체 선택과 출처

선택 우선순위는 다음과 같다.

1. 요청 분이 분석 슬롯과 같은 **검증된 정상 자료**를 우선한다. 기존 현재 슬롯의 45초 판정 컷오프까지 완료되어야 한다.
2. 정확한 슬롯 자료가 없거나 무효이면, 같은 거래일이고 분석 기준시각 전에 이미 정상 저장된 자료 중 최신 요청 자료를 선택한다.
3. 나이는 보수적으로 `collection_started_at`부터 **명목 분석 기준시각 HH:MM:00**까지 계산한다. 600초 이하는 허용하고 초과하면 제외한다. 늦게 저장됐다는 이유로 오래된 자료를 새 자료로 바꾸지 않는다.
4. 대체 자료의 요청·수신·저장 완료 증거는 모두 분석 기준시각 이전이어야 한다. 현재 슬롯의 45초 대기는 과거 자료의 최대 10분 나이를 늘려주는 유예가 아니다. 다음 슬롯/다른 거래일/완료 불명/잘못된 범위/무효 행은 제외한다.
5. 원시 값과 코드·순위·구문 상태, 스냅샷 해시, 환경/시장 조건, 페이지/저장 건수, 완료 증거를 기존 검증기로 검사한다. 페이지 제한만으로 partial인 정상 100행은 허용하면서 부분 수집 상태를 유지한다. 최신 시각이 모호하게 겹치면 임의 ID를 고르지 않는다.

동일 날짜 폴더의 후보를 실제 타임스탬프로 검사한다. 파일명·mtime을 시세 나이로 사용하지 않는다. 저장 완료는 기존 run ID/건수와 ledger mtime 상한 근거를 재사용한다. 이 근거가 없거나 과거 시점의 완료를 증명하지 못하면 보류한다.

`turnover_freshness`에 `exact_slot`, `fallback_within_10m`, `missing`/`ambiguous`, 실제 수집/요청/수신/완료 시각, 나이, 원본 ID/해시, 부분 수집 여부, 거절 사유를 기록한다. C12 내부의 TTL 상태 `fresh`는 호환성을 위해 유지하되 대외 출력에서는 대체 상태를 명시한다. 이를 “현재 시장시각 검증”이나 “최신 실시간”으로 표현하지 않는다.

예시 출력:

```
분석 09:45 / 0198 기준 09:45 / 0186 기준 09:40 (5분 전 대체 자료, 최신 실시간 아님)
0186: 첫 페이지 부분 수집. 전체 시장 순위로 해석하지 않음
```

`paths.turnover`는 실제 사용한 09:40 DB, `paths.turnover_requested`는 원래 찾았던 09:45 DB다. 요청 슬롯 원본 건수와 실제 참고한 건수도 별도 저장한다. 원시 DB·값·수집 시각을 바꾸거나 09:45 자료를 새로 만들지 않는다.

### 흐름 분석 안전장치

09:45 `source_presence['0186']=true`는 참고 자료가 있다는 뜻이고, `fresh_source_presence['0186']=false`는 새 09:45 시세가 없다는 뜻이다. 09:40→09:45와 09:45→09:50의 상승 강도 상태는 `cached_0186_not_new_measurement`로 **판단 보류(C)**한다. 0198 공통 관심 비교(A)는 그대로 가능하다.

기존 C15-10의 09:40→09:50 확보 시점 비교는 유지한다. 같은 09:40 스냅샷을 두 번 사용한 것을 “강세 지속”의 두 독립 시점으로 세지 않는다. 금액 점수는 기존 검증 미완료 정책에 따라 계속 비활성화한다. 09:45 단위 감사도 원래 09:40 DB에서 수행하고 동일 스냅샷 해시를 기록하므로 새 100종목 수집으로 집계하지 않는다.

## D. 운영 반영에 필요한 사항 — 미적용

1. 승인 후 운영 `TURNOVER_SLOTS`에 09:45 하나만 추가하면 수집 일정 보강이 된다. 검토용 **`diagnostics/c15-10b-20261105/runtime-schedule-proposal.diff`**를 만들었으며 적용하지 않았다. 나머지 시각은 유지한다.
2. 운영 버전에는 개발 버전과 다른 재시도·휴장·인증 보호 로직이 있다. 개발 `schedule.py`나 `operating_workflow.py` 전체를 운영에 복사하지 않는다. 일정 한 줄만 병합하고 기존 보호 기능을 회귀 검증해야 한다.
3. 대체 정책은 이번에 **C15 미리보기/흐름 분석 경로**에 구현했다. 기존 운영 `Workflow.morning_review`의 별도 엄격한 후보/알림 경로는 자동 교체하지 않았다. 수집 일정 한 줄만 반영한다고 기존 운영 분석이 이 대체 정책을 자동 사용하지는 않는다.
4. C15 관측 분석을 운영에서 사용할 때는 승인된 C15 패키지·개발 설정을 검토하고 분석 호출 경로에 연결해야 한다. 기존 확정 후보·시총·단위 게이트나 발송 경로를 일괄 완화하지 않는다. 캐시 신선도 표시와 흐름 비교 보류도 함께 반영한다.
5. 기존 프로필 이름/검증 manifest/시작 점검이 서로 맞는지 승인된 배포 절차에서 검증한다. 이번 작업은 `workflow-config.json`의 프로필 이름·발송 설정·페이지 수를 바꾸지 않았다. 재시작·중지·예약 작업 변경도 하지 않았다.

`schedule-inventory.json`에 실제 운영/개발 일정과 운영 코드·설정 해시를 보존했다. 최종 확인에서도 해당 보호 파일의 해시가 같았다. 실행 중인 운영 DB의 파일 해시 불변을 주장하지 않으며, 모든 접근이 읽기 전용임을 테스트했다.
