# Step 5-A — 0186·0181 공식 API 조사와 연동 설계

확인일: 2026-10-26 KST. 프로젝트 기준: `f1b1d22`. 조사·설계 문서이며 수집·정규화·분석 코드, DB·스키마, 인증정보·API 설정·정기 일정은 변경하지 않는다. 시세/순위 API와 OAuth를 호출하지 않았으며 공식 공개 문서만 열람했다. 아래 **공식 확인**, **설계 제안**, **미확인**을 구분한다.

## 1. 결론과 근거의 범위

| HTS 목적 | 확인한 REST TR | 메서드·경로 | 결론 |
| --- | --- | --- | --- |
| 0186 거래대금상위 | `ka10032` 거래대금상위요청 | `POST /api/dostk/rkinfo` | 종목별 거래대금·등락률·현재 거래대금 순위를 함께 제공한다. |
| 0181 전일대비등락률상위 | `ka10027` 전일대비등락률상위요청 | `POST /api/dostk/rkinfo` | 등락률 조건으로 다른 종목 집합을 탐색한다. 거래대금과 명시적 순위 필드는 없다. |

두 TR의 존재·경로·필드는 공식 포털과 공식 저장소에서 확인했다([S1](https://openapi.kiwoom.com/m/guide/apiguide/05/ka10032), [S2](https://openapi.kiwoom.com/m/guide/apiguide/05/ka10027), [S3](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/953e5dbff123f437ab4d11a78a95191a685eb51f/kiwoom/_data/kiwoom_api_spec.json)). HTS 화면의 목적도 [0186 공식 도움말](https://download.kiwoom.com/hero4_help_new/0186.htm)과 [0181 공식 도움말](https://download.kiwoom.com/hero4_help_new/0181.htm)로 확인했다.

0181은 최신 포털의 `stk_cls` 설명에 영웅문4 [0181]이 직접 언급된다. 0186은 동일한 기능명·필드의 REST 대응으로 판단할 수 있으나 **화면과 REST 결과의 완전한 동일성 선언이나 동일 시점 실측은 확인하지 않았다.** 시장·거래소·제외 조건·장 구간·정렬을 맞춘 HTS 대조가 필요하다. 0198도 기존 사용자 실증 결과와 공식 문서의 대응 선언은 구분한다.

**설계 제안:** 0186 연동을 먼저 검증하고 0181은 거래대금 상위 집합 밖의 급등주·정찰 관찰을 위한 별도 확장으로 둔다. REST가 확인됐으므로 현재 환경에 OpenAPI+ OCX를 새로 도입할 이유는 없다. OpenAPI+는 [공식 이용 안내](https://www.kiwoom.com/h/customer/download/VOpenApiInfoView)와 KOA Studio에서 별도 확인 가능한 대안이지만, `opt`/`ka` 번호 유사성만으로 TR 대응·제약을 전용하지 않는다.

## 2. 응답 필드 대조 — 공식 확인

| 항목 | ka10032 / 0186 | ka10027 / 0181 | 기존 ka10095 시세 |

| 순위 | `now_rank` 현재 거래대금 순위, `pred_rank` 전일 거래대금 순위 | 전용 필드 없음 | 시장 거래대금/등락률 순위 없음 |

ka10032·ka10027의 필드는 모두 선택 항목이다. 필드가 명세에 있다는 사실은 실응답의 제공·정확성·신선도 검증 완료가 아니다. 거래대금이 없는 ka10027 응답에서 `현재가 × 거래량`으로 거래대금을 만들어 내지 않는다. 위 필드와 의미는 [ka10032 포털](https://openapi.kiwoom.com/m/guide/apiguide/05/ka10032), [ka10027 포털](https://openapi.kiwoom.com/m/guide/apiguide/05/ka10027), [ka10095 공식 명세](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/953e5dbff123f437ab4d11a78a95191a685eb51f/kiwoom/_data/kiwoom_api_spec.json)에서 대조했다.

### 혼동하기 쉬운 필드

- `pred_rank`는 **전일** 순위다. 직전 장중 회차 순위는 저장된 직전 성공 관측의 `now_rank`로 따로 계산해야 한다.
- ka10027의 `cnt`는 최신 포털에서 순위에 포함된 **일수**로 설명한다. 상승률 정렬의 1은 첫 진입일, 2는 연속 이틀의 예다. 기존 TOP5 장중 출현/연속 횟수로 쓰지 않는다. 다른 정렬의 상세 해석은 별도 검증한다.
- ka10027에는 `rank`·`now_rank`가 없다. 페이지와 행 위치는 `source_row_position`으로 보존할 수 있으나 이를 공식 절대 순위로 바꾸지 않는다. 동률 처리·전체 페이지의 정렬 안정성도 미확인이다.
- `stk_cls`의 증/신/펀 표기용 값으로 업종·섹터를 생성하지 않는다. `cntr_str`은 체결강도이며 거래대금·주문 체결 가능성과 별도다.
- 0198의 `base_comp_chgr`·`prev_base_chgr`는 조회순위 기준 시점의 대비값이다. 두 TR의 전일대비 `flu_rt`와 동일 지표로 간주하지 않는다.

### 단위·누적 기준·시각

**공식 확인:** ka10032의 거래대금은 백만원, 두 TR의 거래량은 주, 현재가·대비·호가는 원, 등락률은 %다. 현재가 등 가격에는 부호가 포함된다. `pred_pre_sig`는 상한/상승/보합/하한/하락을 구분한다. 금액 환산은 검증 후 Decimal로 `백만원 × 1,000,000`을 적용하며 원본을 보존한다. ka10095의 공식 거래대금 단위도 백만원이다.

**미확인:** 확인한 두 TR의 설명에는 거래대금/현재거래량의 정확한 누적 시작·리셋 시각, KRX/NXT 통합 집계 범위, 정규장·장전·장후 포함 여부, 서버 갱신 지연·행별 시각이 명시돼 있지 않다. 요청에 순간/구간/과거 날짜 선택 인자도 없다. 따라서 장중 누적값으로 관찰하는 것은 **검증 대상 해석**이며 순간 거래대금·분당 유입액을 제공한다고 볼 수 없다. API의 전일 순위·전일 거래량이 현재 값의 거래일을 증명하지도 않는다.

**설계 제안:** 원본 금액과 공식 단위 선언은 저장하되 실측 단위 검증, 누적 기준, 거래일/시각 검증 상태를 분리한다. 구간 차감은 같은 범위·동일 거래일·누적 리셋/정정 검증 후의 별도 후속 설계다. 현행 가격 부호 보존·정규화 보류 정책도 완화하지 않는다.

## 3. 조회 조건과 시장·제외 설정

공식 요청 표의 모든 본문 인자는 필수이며 문자열이다. 아래 값은 API의 허용 조건 설명으로서 STOCK1의 새 수집 설정을 적용한 것이 아니다.

| 공통 | `mrkt_tp` | `000` 전체, `001` 코스피, `101` 코스닥 |

| ka10027 | `trde_qty_cnd` | `0000` 전체, `0010` 1만주 이상 등 거래량 하한 선택 |

전체 enum 원문과 길이는 위 [공식 ka10027 요청 표](https://openapi.kiwoom.com/m/guide/apiguide/05/ka10027)에 있다. `stk_cnd`를 비트 마스크나 다중 조건 배열로 취급하지 않는다. 예를 들어 16과 4를 임의로 합쳐 여러 제외 조건을 요청하지 않는다. '스펙제외'의 정확한 종목 범위와 다른 조건의 동시 적용 가능성은 키움 확인 대상이다.

ka10032 요청에는 ETF·ETN·우선주·SPAC·정리매매를 각각 제외하는 별도 인자가 없다. 관리 제외만으로 이들이 전부 제외됐다고 판단하지 않는다. 별도 종목 정보로 사후 필터링하려면 그 정보의 기준일·검증을 먼저 확보하고 원래 API 순위와 필터 후 표시 순서를 구분한다. ka10027과 ka10032의 필터가 다르면 교집합 밖 종목을 유동성 부족·등락 부재로 해석할 수 없다.

**설계 제안:** 첫 검증은 전체 시장·관리 제외·KRX 등 하나의 명시적 프로필로 범위를 고정하고, 필요하면 코스닥 프로필을 별도로 검토한다. 이는 적용 결정이 아니다. 0198에는 동일한 시장/거래소 지정 인자가 없으므로 모집단의 완전한 동일성을 가정하지 않는다. ka10095의 `039490` / `_NX` / `_AL` 구분과 신규 TR의 거래소 조건도 별도 대조한다.

**공식 안내의 주의점:** 최신 모의투자 안내는 매매·계좌조회는 KRX, 시세는 모의에서도 NXT 제공이라고 구분한다. 반면 TR 상세 기본정보에는 모의 도메인 옆 KRX 지원 문구가 있다. 이를 근거로 두 순위 TR의 모든 거래소 조합을 지원한다고 확정하지 않는다. 우선 KRX를 검증하고 NXT/통합은 각각 확인한다. 모의 성공을 실전 검증으로 승격하지 않는다. 근거: [모의투자 이용안내](https://openapi.kiwoom.com/intro/mockInvestInfo?dummyVal=0).

## 4. 페이지·결과 수·인증·호출 제한

**공식 확인:** JSON POST이며 `Content-Type: application/json;charset=UTF-8`, TR별 `api-id`, Bearer 접근토큰을 사용한다. 실전/모의 도메인은 각각 `https://api.kiwoom.com`, `https://mockapi.kiwoom.com`이다. 환경별 앱키·시크릿키와 서비스 신청이 필요하다. 토큰 발급은 별도 OAuth 절차이며 이번 조사에서는 하지 않았다. 인증 근거는 [공식 OAuth 가이드](https://openapi.kiwoom.com/m/guide/apiguide)와 각 TR의 요청 헤더 표다.

응답 헤더 `cont-yn=Y`이면 같은 요청 조건에 응답의 `cont-yn`과 `next-key`를 전달해 다음 페이지를 요청한다. 현재 명세에 요청 결과 개수/상위 N개를 정하는 필드는 없다. **페이지당 행 수·총 최대 행 수·모든 종목 반환 보장·순위가 고정되는 스냅샷 보장은 미확인**이다. 예시의 3/4행을 결과 개수로 보지 않는다. 공식 예제의 `MAX_PAGES=10`과 대기 0.2초도 샘플 코드의 선택이며 서버 최대 페이지·허용 유량의 보장이 아니다([ka10032 예제](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/examples/국내주식/순위정보/get_domestic_trading_value_top.py), [ka10027 예제](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/examples/국내주식/순위정보/get_domestic_prev_day_change_rate_top.py)). 예제는 인증을 자동 수행할 수 있으므로 조사에서 실행하지 않았다.

[공식 서비스 안내](https://openapi2.kiwoom.com/intro?dummyVal=0)는 국내 조회 TR을 계좌별/토큰별 초당 5회, 모의는 계좌별/토큰별 동일 TR당 초당 1회로 안내한다. 개별 TR의 추가 한도·분/시간/일 누적 한도와 순간 버스트 허용량은 이번 근거에서 확정하지 않았다. 기존 프로세스와 합산해야 하며 미국주식 한도를 국내에 적용하지 않는다. 샘플의 0.2초 간격은 모의 동일 TR 연속조회에 그대로 사용하지 않는다.

**설계 제안:** 후속 구현 시 현재 자원 잠금·유량 제어와 공유되는 대기열을 설계한다. 페이지/재시도도 각각 호출로 계산한다. 반복 키·빈 키의 Y·모순된 순위/중복 코드·중간 실패·상한 도달은 partial/오류로 남기고 전체 수집 완료로 표시하지 않는다. 페이지별 원본·행 위치와 수집 구간을 보존하고, 바뀐 순위를 마지막 값으로 조용히 덮어쓰지 않는다. 조회 결과에 없다는 사실과 API 미제공·필터 제외·미수집을 구분한다. 429·인증·제한 오류 시 중단/재시도 정책은 후속 범위이며 현재 수집기를 변경하지 않는다.

### 호출량 예산 — 설계 계산, 현재 일정 변경 아님

기존 방식의 보수적 비교 예는 0198 한 번 + ka10095 20종목/2종목씩 10번 = 회차당 11번, 하루 10회 110번이다. 모든 시세가 새 요청을 요구하고 각 TR 첫 페이지로 충분하며 인증·재시도는 제외한 예산이다. 실제 호출량은 저장 이력·누락·연속조회에 따라 다르다.

| 추가 조회 가정 | 하루 추가 호출 | 기존 예산 포함 |
| --- | --- | --- |
| ka10032만, 같은 10회·1개 프로필·매번 1페이지 | 10 | 120 |
| ka10032와 ka10027, 각각 1페이지 | 20 | 130 |
| 두 TR 각각 2페이지 | 40 | 150 |
| 두 TR을 코스피/코스닥 별도 프로필로 각각 1페이지 | 40 | 150 |

일반식은 `추가 = Σ(실행 프로필별 실제 페이지 수 + 재시도 수)`다. TR을 늘려도 기존 ka10095 10요청을 당장 없애거나 순위 밖 종목을 무료로 확보한다고 계산하지 않는다. 신규 정찰 종목 시세 조회는 별도 비용이다. 같은 프로필을 10회 검증한다는 가정일 뿐 새 수집 일정을 승인·등록한 것이 아니다.

예를 들어 전체를 시작 간격 1.2초의 단일 대기열에 놓는 설계라면 13요청의 첫~마지막 시작 간격은 최소 14.4초다. 이는 기존 코드의 간격을 변경한 값이 아니며 HTTP 응답·인증·재시도 시간은 추가다. 페이지가 늘면 교차 조회 시차가 커지므로 유량뿐 아니라 시간 예산도 중단 기준으로 검토해야 한다.

## 5. 0198·ka10095 재사용과 0181 추가 필요성

| 사용 목적 | 재사용/추가 데이터 | 판단 |
| --- | --- | --- |
| TOP20 섹터 군집·TOP5 반복 | 기존 0198·Bubble 지표 | 그대로 유지. 외부 순위 집합으로 기존 분모·TOP5를 바꾸지 않는다. |
| 거래대금 상위에 이미 포함된 핵심주의 금액·전일대비 등락률 | ka10032 | 한 응답에서 함께 확보 가능. 이 목적만이면 ka10027의 동일 종목 등락률 추가 조회는 필수 아님. |
| TOP20/TOP5이나 ka10032 결과 밖인 종목의 시세 | 기존 ka10095 | 시세·금액 검증 근거로 유지. 금액 값만으로 시장 거래대금 순위를 만들 수 없음. |
| 거래대금 상위 집합 밖의 급등주·정찰 관찰 | ka10027 상승률 프로필 | 독립적인 모집단이므로 추가 가치가 있음. ka10032 결과를 등락률순으로 정렬하는 것과 다름. |
| ka10027 종목의 거래대금·시각 확인 | ka10032 교집합 또는 추후 승인된 지정 시세 | ka10027 단독으로는 금액을 확보하지 못함. 기존 TOP20 시세 범위 밖이면 별도 조회 계획 필요. |

재사용할 수 있는 것은 기존 날짜·환경·종목·시각 검증, 원본 보존, Decimal 정규화 원칙, 배치·실패 관리와 출처 표시다. 새 TR의 단위/시각 검증 상태를 기존 ka10095 결과에서 복사하거나 현행 normalized_json 버전을 새 TR에도 유효하다고 가정하지 않는다. 기존 ka10095의 최신 단일 배치 및 누락 보충 금지 정책은 유지한다. 이번 조사로 시세 수집을 대체·축소하지 않는다.

정찰 관찰은 가령 `등락률상위 집합 − 조회순위 TOP20` 등 별도 관찰 집합으로 제안할 수 있다. 해당 종목이 나중에 0198 TOP5에 실제 진입하기 전에는 TOP5 핵심주로 승격하지 않는다. '급등 초기 선행주'라는 인과·예측도 증명하지 않는다. 기존 섹터 태그가 없으면 미분류로 남긴다.

기존 `collections`·`ranking_records`의 0198 의미와 순위를 재사용해 다른 순위를 덮어쓰지 않는다. 후속 저장 구조는 아래와 같이 별도 관측 단위로 설계하고 구현 전에 DB 호환성을 따로 검토한다.

섹터별로 기존 TOP20 고유 수·TOP5 수와 별도로 '조회/금액 교집합', '조회/등락률 교집합', '세 집합 공통 관측'을 설명적 집계로 둘 수 있다. 다중 태그는 섹터 내 코드 1회, 전체는 고유 코드 1회이며 태그 자동 통합은 없다. 외부 표본 전체를 기존 TOP20 섹터 수에 섞지 않는다. 커버리지는 검토 대상 TOP20/TOP5 중 적합한 근거가 있는 고유 코드 수/대상 수이며, 결과 밖·필터 제외·미수집을 별도로 표시한다. 시장 전체 유동성 분모로 확대 해석하지 않는다.

## 7. 코드·시점 교차 검증 설계

1. 원본 종목코드를 보존하고 검증된 표준 코드와 거래소를 별도 관리한다. 이름은 진단용이다. 선행 0을 제거하지 않으며 `_NX`·`_AL`을 무조건 잘라 KRX와 합치지 않는다. 현재 코드 파서가 허용하는 6자리 영숫자/거래소 접미어도 해당 TR의 실응답·공식 코드 정의와 대조한 뒤 연결한다. 미지원·불일치 코드는 보류한다.
2. 같은 KST 거래일·환경·운영/테스트·거래소 조건을 먼저 대조한다. 시장/제외 프로필이 다르면 범위 불일치를 기록한다. KRX·NXT·통합 값을 더해 중복 거래대금을 만들지 않는다. 0198의 모집단 범위 미확인은 종목별 시세의 거래소 확인과 별도다.
3. 요청 시작/완료를 각각 저장하고 페이지 전체의 최소 시작~최대 완료 구간을 보인다. **HTTP 요청 시각·서버 Date 헤더를 종목 체결/가격 기준 시각으로 바꾸지 않는다.** 두 순위 TR에는 현재 확인한 날짜/시각 필드가 없으므로 서버 기준 동일 시점 검증은 불가다. 요청이 가까운 관측이라는 잠정 연결과 서버 시각까지 검증된 연결을 구분한다.
4. **허용 시차 제안:** 새 관측의 `max_request_gap_seconds`와 페이지 전체 소요 예산을 별도 매개변수로 두고 실측 후 결정한다. 초기 테스트 목표 30초, 비교 후보 60초/300초 등은 설계 실험값이며 공식 허용치·운영 기본값이 아니다. 기존 v2의 ±300초 검증 규칙을 새 TR에 그대로 통과 도장으로 사용하지 않는다. 기준 시각이 없으면 시차가 작아도 시간 검증 완료로 승격하지 않는다.
5. 과거 시각 `t`를 재생할 때 요청 완료가 `t`를 넘는 신규 관측은 당시 근거로 사용하지 않는다. 현재 Step 4-F의 엄격한 선택 시각 정책은 유지한다. 나중에 모은 근거를 함께 보려면 별도의 '관측 묶음 완료 시각'으로 명시하고 당시 화면과 구분해야 하며, 기존 HTML을 소급 보정하지 않는다.
6. 같은 코드의 ka10032·ka10095 금액은 단위 검증 후 원 단위 Decimal로 대조한다. 서로 다른 시점의 누적 금액은 같아야 한다고 단정하지 않는다. 허용 오차는 문서/실측 후 정하고 차이·시간 차이·갱신 순서를 남긴다. 등락률은 전일대비 기준끼리 비교하되 반올림·거래소·기준일 차이를 확인한다. 가격은 부호 의미가 확인되기 전 절댓값으로 임의 비교하지 않는다.
7. 값의 일치만으로 단위·시점·유동성이 검증된 것은 아니다. 단위, 실측 값, 기준일/시각, 표본 커버리지, 주문 규모 대비 유동성을 각각 통과해야 매매 후보 분류를 검토한다. 현재 확보한 문서만으로는 '조회 관심도 기반 핵심 관찰종목 — 매매 후보 미확정' 상태를 유지한다.

## 8. 후속 검증 순서와 보류 항목

이번에는 실행하지 않은 후속 계획이다. 실제 API/OAuth·일정 연결·DB 변경은 각각 별도 승인 범위다.

1. 공식 포털/키움 확인으로 최대 반환 수·페이지 안정성·누적 기준/리셋·장 구간·시장별 코드·서버 시각 대안·정확한 모의 지원 범위를 먼저 보완한다. ka10027의 행 순서·동률·cnt의 정렬별 의미도 확인한다.
2. 기존 수집기와 충돌하지 않는 별도 승인된 검증 환경에서 한 프로필·첫 페이지의 원본/헤더를 보존한다. 단위·코드·양/음/0/누락 필드와 인증·유량 제한을 확인한다. 공식 예시의 중복 코드와 가격 값은 실응답 근거로 쓰지 않는다.
3. 장중 여러 시각에 같은 설정의 HTS 0186/0181 및 ka10095와 대조한다. 장전/장후/휴일에는 전일값·정지·빈값을 오늘 데이터로 오인하지 않는지 확인한다. 현재가×거래량으로 금액을 검증하지 않는다.
4. 별도 허용된 다중 페이지 검증에서 중복·순위 이동·키 반복·중간 실패·부분 수집·시간 예산 초과를 확인하고 호출량을 측정한다. 단위와 순위의 실증은 mock/real을 나눠 기록한다.
5. 오프라인 fixture로 시간 차이·미래 배제·거래소/프로필 분리·TOP5 전환·다중 태그·부분 커버리지·정찰 집합과 기존 레이더 회귀를 검증한 뒤 구현 범위를 결정한다. 현재 10회·시세 연동·DB 스키마는 유지한다.
