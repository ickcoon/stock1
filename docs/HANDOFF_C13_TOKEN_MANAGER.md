# C13 토큰 자동관리 운영 인계

2026-10-31 KST. 기준 커밋 75bc5c8157291470af5d2614c140de1477c356fa 이후 C13/C13-B 구현과 검증을 GitHub에 보관하는 문서다.
운영 적용은 하지 않았다. 운영 stock1·DB·수집기·작업 스케줄러·기존 미추적 파일은 보존한다.

## 구조와 호환성

- 기존 Credentials가 mock/real 호스트를 선택하고 KiwoomClient.authenticate가 OAuth 응답 expires_dt를 KST로 해석한다. 발급 파서는 중복 구현하지 않았다.
- TokenManager가 재사용·갱신·제한 재시도·대기 상태를 관리한다. OAuthProvider는 기본 단발 발급 계약을 유지하며 auto_refresh=True일 때만 같은 관리자를 사용한다.
- 장기 0198 수집은 ensure_token을 사용한다. 0186/시세는 기존 단발 발급·조회 무재시도 예산을 보존한다. 관리자를 명시적으로 주입하거나 보호 캐시를 활성화할 수 있다.
- ka10001은 ManagedInfoTransport를 기존 IndependentClient에 주입한다. 주문 endpoint는 허용하지 않는다.
- 캐시 기본값은 비활성이다. 장기 collect의 --protected-token-cache 옵션으로만 디스크 저장/프로세스 잠금을 명시적으로 켠다. --test-now와의 조합은 거부한다.

## 실제 만료와 10분 전 정책

요청 직전 expires_dt를 검사해 남은 시간이 600초 이하면 갱신하며 충분히 유효하면 재사용한다. 발급 시각+24시간을 임의 계산하지 않는다.
유휴 상태에서 정확히 만료 10분 전을 맞추는 백그라운드 발급은 하지 않는다. 다음 요청 직전에 검사하므로 장외 OAuth나 별도 스케줄은 추가되지 않는다.
발급된 토큰의 수명이 필요한 여유 시간보다 짧으면 시간을 연장하거나 기존 토큰으로 우회하지 않고 실패한다.

## 보호 캐시·계정·권한

경로는 %LOCALAPPDATA%/Stock1/token-cache다. 환경·앱 식별 hash별 .token-cache.bin을 사용하며 App Key/Secret 원문은 저장하지 않는다.
파일 내용 전체를 Windows 사용자 DPAPI로 암호화한 후 원자적으로 저장한다. LOCAL_MACHINE 옵션 및 평문 fallback은 없다.
디렉터리 ACL은 사용자 프로필의 기본 권한을 상속하며 코드에서 별도 DACL을 강제하지 않는다. 사용자 지정 root는 공유/Git 폴더가 아닌 같은 수준의 보호된 로컬 폴더여야 한다.
실행 계정의 프로필이 로드돼야 한다. 관리자 실행이 필수 조건은 아니다. 서로 다른 사용자/PC 간 캐시 공유·전송은 하지 않는다.
mock/real 및 App Key별 파일과 잠금이 분리된다. Secret까지 포함한 binding이 맞지 않으면 거부한다. 다른 환경 토큰으로 fallback하지 않는다.
Secret 회전/계정 변경/손상 캐시는 자동 삭제·덮어쓰기하지 않는다. 해당 사용자의 캐시 처리와 재인증은 별도 운영 절차로 결정한다.

같은 앱/환경을 사용하는 장기 프로세스는 같은 Windows 사용자와 cache root를 사용해야 한다. 잠금 안에서 다시 캐시를 읽으므로 정상 동시 발급을 방지한다.
잠금 대기는 기본 2초다. 기존 발급이 오래 걸리면 다른 수집 회차는 cache_busy로 실패할 수 있다. 다른 프로세스가 만든 최신 토큰은 오래된 요청의 인증 실패로 지우지 않도록 값 일치 조건으로 폐기한다.

## 작업 스케줄러 실행 계정 확인 — 읽기 전용

작업 스케줄러에서 기존 작업의 일반 탭 → 보안 옵션의 실행 사용자, 로그온 여부 옵션을 확인한다.
동작 탭에서는 Python 실행 파일·작업 폴더·수집 인수만 확인한다. 자격증명을 명령줄에 넣거나 전체 명령줄/환경/토큰을 공유하지 않는다.
아래는 기존 작업 이름을 대입하는 읽기 전용 확인 예시이며 작업을 실행·중단·수정하지 않는다.

```powershell
Get-ScheduledTask -TaskName '<기존 작업 이름>' |
  Select-Object TaskName, State,
    @{Name='RunAs';Expression={$_.Principal.UserId}},
    @{Name='LogonType';Expression={$_.Principal.LogonType}}
```

운영 전에는 실제 실행 계정으로 사용자 프로필·LOCALAPPDATA·캐시 폴더 ACL·합성 DPAPI 복원을 확인한다. 대화형 로그인 계정에서 성공했다는 사실만으로 스케줄러 계정 복원을 보장하지 않는다.
PC 시각/시간대/동기화 상태도 확인하되 이번 인계 작업에서 변경하지 않는다.

## 실패·진단

- 통신/시간 초과와 일시적 서버·호출 제한: OAuth raw 시도 최대 2회. 기본 중간 대기 1초, 숫자 Retry-After는 최대 60초를 존중한다. 그보다 긴 요구는 중단한다.
- TLS/인증 거절/응답 형식 오류는 무제한 재시도하지 않는다. 최종 통신 장애는 60초, 인증 등 장애는 300초 대기한다. 발급 전 암호화한 in-flight 표식은 중단·충돌 시 즉시 연속 발급을 제한한다.
- 0198은 기존대로 인증 거절 시 새 토큰으로 1회만 재조회한다. 다시 실패하면 대기하며 이전 토큰으로 반복 요청하지 않는다.
- 0186·시세·ka10001의 단발 경로는 인증 거절 시 폐기하고 조회를 재실행하지 않는다. 기존 정상 수집 이력은 보존하고 현재 실패 회차를 error로 남긴다.
- 진단에는 환경·만료 시각·고정 오류 category·성공/실패 회차만 사용한다. 키·토큰·인증 헤더·서버 메시지 원문·캐시 복호화 내용은 출력하지 않는다.
- cache_busy는 실행 계정/root 중복과 동시 작업을, unreadable/scope_mismatch는 사용자 프로필·환경·키 변경을, network/tls는 연결·인증서 상태를 구분해 점검한다. 캐시 삭제·보호 해제·재시도 반복으로 우회하지 않는다.

## 서버 측 미검증 및 운영 전 조건

새 토큰 발급 시 같은 App Key의 기존 토큰이 서버에서 계속 유효한지는 미검증이다. 다른 PC/계정은 로컬 잠금을 공유하지 않으며, 서버가 응답을 잃은 발급을 처리했는지도 로컬에서 확정할 수 없다.
운영 수집기가 기존 메모리 토큰을 사용 중인 상태에서 같은 키로 새 캐시 사용 프로세스를 병행 실행하지 않는다. 별도 앱/키 또는 명시적 인증 운영 정책을 먼저 확정한다.

실제 OAuth/API 검증은 별도 승인 단계다. 같은 실행 계정의 재부팅 후 복원, 충분한 유효기간의 재사용, 10분 경계의 갱신, 인증 장애·잠금 장기화 시 수집 회차 처리 등을 검증해야 한다.
이번 테스트는 실제 Windows DPAPI에 합성 값만 저장했다. 실제 재부팅·실서버 장시간 지속성·다른 계정 복원은 실측하지 않았다.

## 배포·롤백 절차 — 이번 단계에서는 실행 금지

1. 검토한 배포 커밋과 마지막 정상 코드(기준 75bc5c8 또는 운영에서 별도 확인한 버전), 원래 실행 인수/작업 설정을 기록한다. 기존 DB 백업이 필요하면 승인된 SQLite Online Backup 절차를 사용하며 실행 중 .db만 복사하지 않는다.
2. 별도 승인된 배포 창에서 코드만 적용한다. .env/DB/기존 수집 이력/스케줄은 덮어쓰지 않는다. 합성 DPAPI 검증 후 승인된 실제 최소 조회로 확인한다.
3. 장애 시 자동 재발급/재실행을 반복하지 않고 정상 회차와 실패 category를 보존한다. 보호 캐시 옵션을 끄는 것만으로 서버의 이전 토큰 유효성이 복원되지는 않는다.
4. 롤백은 승인된 배포 창에서 기록한 정상 코드와 원래 실행 인수/작업 설정으로 복구한다. reset --hard/clean/강제 push는 사용하지 않는다. DB를 과거 상태로 되돌리거나 토큰 폐기 API를 호출하지 않는다.
5. 캐시를 삭제/전송/복호화하지 않고 원래 권한으로 보존한다. 구버전의 새 OAuth 발급도 다른 프로세스에 영향을 줄 수 있으므로 인증 정책과 실행 계정 확인 후 재개한다.
